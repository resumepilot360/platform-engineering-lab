# ADR-0008: External Secrets Operator + OpenBao; secretbox encryption at rest

- Status: Accepted (2026-10-28)

## Options considered

| Option | RAM | Fidelity to AWS target | Notes |
|---|---|---|---|
| **ESO + OpenBao, standalone, raft storage** | ~0.4 GiB | ESO layer identical; store differs | Real init/unseal, policies, k8s auth, audit, persistence |
| ESO + HashiCorp Vault | same | same | BSL licence since 2023; equivalent API |
| ESO + Vault/OpenBao dev mode | ~0.3 GiB | lower | In-memory, wiped on restart, root token in pod args |
| ESO + LocalStack Secrets Manager | ~0.5 GiB | API shape matches | IAM not enforced by default, so access tests would mislead |
| Sealed Secrets / SOPS | low | different model | Encrypted values in Git; complements GitOps but is not an external store |

## Decision
1. **ESO v2.14** delivers secrets as Kubernetes Secrets through **namespaced**
   `SecretStore`s, one per environment namespace, each with its own
   permissionless ServiceAccount. No ClusterSecretStore, so no cross-namespace store.
2. **OpenBao 2.7** (open-source Vault fork), standalone, integrated raft
   storage on a PVC, Shamir 3/2 manual unseal, audit device to stdout.
   Configuration as code: `platform/secrets/openbao/{policies,roles}`, applied
   by `scripts/openbao-bootstrap.sh` over the HTTP API.
3. **K3s encryption at rest** with the `secretbox` provider.
4. Secret values are generated by scripts, never written to Git.

## Consequences
- See docs/secrets-model.md §4 for accepted limitations: key colocated with
  data, unseal keys in one file, no TLS, namespace boundary, no HA.
- On AWS only the `SecretStore.spec.provider` block changes. ExternalSecrets
  and the consuming workloads are portable.
- After a restart OpenBao needs an unseal (`openbao-bootstrap.sh --unseal`). ESO
  keeps serving the last synced Secret.
